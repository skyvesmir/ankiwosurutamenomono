## 2. アルゴリズム妥当性(A)

### 2.1 FSRS-7実装は参照実装と一致 ✅

`fsrs.js` の各数式を open-spaced-repetition/srs-benchmark の `fsrs_v7.py` と照合した。

- **忘却曲線(二重べき乗混合)**: `retrievability()` は w27–w34 を使う2曲線の重み付き混合で、FSRS-7の新形式。従来のFSRS-4.5単一曲線ではなく最新式を採用している(fsrs.js内 `makeEngine` の retrievability 定義)。
- **初期安定性**: `initStability(g) = W[g-1]`(fsrs.js、DEFAULT_W[0..3]) — 参照実装と一致。
- **初期難易度**: `W4 − e^(W5·(g−1)) + 1` — FSRS-5以降の指数形式に一致。
- **難易度更新**: 線形ダンピング + `init_d(4)` への1%平均回帰 — 参照実装の mean reversion と一致。
- **安定性更新の短期/長期分岐**: 同日復習(elapsed < 0.5日)は base=16、通常復習は base=7 の別式 — FSRS-7の短期記憶モデルに一致。
- **間隔逆算**: 二重べき乗曲線は閉形式で逆算できないため60回の二分探索(`intervalFromStability`) — 数値的に正当(検証は §3)。
- **ファズ**: 間隔≥3日で±5%、下限2日(`schedule()`内) — Ankiのfuzz慣行と同等。`preview()` はファズ無しで表示用に分離されており、**表示と実スケジュールの乖離を防ぐ設計として正しい**。

### 2.2 復習キュー方針に明確な根拠 ✅

`session.js:48-59` — 復習は Retrievability 降順でソート:

```js
// session.js:53-59
due.forEach(c => { ... rNow[c.id] = FSRS.retrievability(elapsed, st.stability || 0.001); });
due.sort((a, b) => rNow[b.id] - rNow[a.id]);
```

コメント(session.js:48-52)にAnki公式フォーラムのシミュレーション結果("descending retrievability" が同一保持率を最小学習時間で達成)を引用しており、バックログ時に特に有効な選択。**根拠の明示まで含めて妥当**。

「復習が全デッキで完了するまで新規を出さない」(session.js:73-75 + `hasGlobalDueReviews` session.js:15-24)も、復習債務の蓄積を防ぐ保守的で正しい方針。

### 2.3 出題形式ポリシーの設計上の注意点 🟡

`session.js:99-108` — 新規カードは選択式(MC)、復習は強制的に記入式(type-je)。能動的想起の強制として教育学的には正しい。ただし**FSRSは「grade の意味が全レビューで均質」であることを暗黙に仮定**しており、本アプリでは:

- 新規(初回): MC で正解しやすい → grade 3 が出やすい
- 復習: タイピングで難しい → grade 1/2 が出やすい

という**形式起因の系統的グレードシフト**が存在する。これは初期安定性(W[0..3])の推定を楽観側に、以降の観測保持率を悲観側に歪める。幸い、ログに `format` を記録しているため(session.js:374-381)、**オプティマイザが将来この差を吸収・分析できる下地はある**。現状は「既知の設計トレードオフ」として許容範囲(オプティマイザが W を個人化すれば大部分は補正される)。

### 2.4 Again 再出題ループ ✅

grade=1 のカードはセッション末尾に再追加され(session.js:391)、記入式で正解するまで `againIds` マークが外れない(session.js:392-393)。FSRS側でも grade=1 → relearning・due=+60秒(fsrs.js `schedule()`)と整合しており、**セッション内学習ステップとして機能的に正しい**。

### 3.2 🔴 記入採点の重大欠陥(実証済み)

`quiz.js:33-38` の `normalize()` は `～ . , ! ? : ; ' " -` を除去するが**括弧 `()` を除去しない**。`quiz.js:42-55` の `acceptableAnswers()` も括弧の展開(有無両方の受理)を行わない。実行結果:

```
"work on (～)"             ← "work on"                => FAIL
"(every) once in a while"  ← "once in a while"        => FAIL
"(every) once in a while"  ← "every once in a while"  => FAIL  ★どう打っても不正解
"on occasion(s)"           ← "on occasion"            => FAIL
"play a role/part (in ～)"  ← "play a role"            => FAIL
"a great/good deal (of ～)" ← "a good deal"            => FAIL
```

**影響範囲(実データ計測)**: 括弧を含む term は `phrases_full.json` で **108/3238件**、`phrases_target.json` で **104/1000件**。これらは記入式(＝全復習カード)で**ユーザーが何を打っても不正解**になる。編集距離1の「おしい」救済(session.js:275)も `"work on"` vs `"work on ()"` は距離3のため発動しない。

**これは単なるUX問題ではない**: 誤った grade=1 がデフォルト提示され(session.js:331)、そのまま (a) FSRSの安定性を不当に破壊し、(b) 最適化用ログを汚染する。**アルゴリズム基盤への入力汚染として最重大**。

さらに `acceptableAnswers()` はスラッシュを**最初の1組しか展開しない**(quiz.js:46-53 の `match(/(\S+)\/(\S+)/)` は非グローバル)。3語連結スラッシュでは:

```
"look back on/upon/to ～" ← "look back to" => OK
"look back on/upon/to ～" ← "look back on" => FAIL  ★"on/upon"が未分解のまま残る
```

該当データ: 2組以上のスラッシュを含む term は phrases_full に6件(`make/earn a/one's living` 等)。

**推奨修正**(互換・低リスク):
1. `normalize()` に `.replace(/[()（）]/g,'')` を追加
2. `acceptableAnswers()` で `(...)` 部分の「有り/無し」両形を生成
3. スラッシュ展開を `a/b/c` 全組み合わせ・全出現箇所に拡張

### 3.3 🟡 セッション進捗表示の軽微な不整合

`session.js:131-134` で reAdd(Again再出題)は `s.queue` に追加されるが `s.total` は初期値のまま。`renderQuestion`(session.js:153, 159)のカウンタは `Math.min(s.idx+1, s.total)` でクランプされるが、プログレスバー幅 `s.idx/s.total*100` は100%超になり得る(親の `overflow-hidden` で視覚的破綻は回避)。実害は小さいが、再出題分を `total` に加算するのが正確。

## 4. optimizer.js の統計的健全性(D) — 本レポートの中核

### 4.1 設計の正確性 ✅

- **損失関数**(optimizer.js:66-97 `computeLoss`): レビュー系列をFSRSでリプレイし、`y = grade>1` の二値ログ損失。`p` を `[1e-6, 1−1e-6]` にクランプ、`elapsed < 0.5日`(同日復習)を評価から除外 — **FSRSベンチマーク(srs-benchmark)の標準評価プロトコルと同一**であり正確。
- **時系列ホールドアウト**(optimizer.js:42-61 `buildSequences`): `cutoff = logs[⌊0.75n⌋].reviewed_at` で時刻分割し、**学習=過去75% / 検証=未来25%**。ランダム分割ではなく時系列分割を選んでいるのは、系列内リーク(同一カードの過去→未来依存)を防ぐ上で**教科書的に正しい**。
- **パラメータ束縛**: `OPT_IDX = [0..15]`(optimizer.js:25)で w16–34(検索重み・忘却曲線形状)を凍結。個人データ数百件でこれらを動かすとノイズ過敏になるため、**分散削減として妥当な判断**(コメントにも根拠明記)。`BOUNDS` による各パラメータのクリップも発散を防ぐ。
- **座標降下**(optimizer.js:104-134): 4パス × 乗算候補 `[0.7, 0.85, 0.95, 1.05, 1.2, 1.45]`、改善1e-6未満で早期終了、`setTimeout(0)` でUI非ブロック。勾配不要・実装単純・16次元では十分実用的。

### 4.2 「改善しない場合は適用しない」基準の実験的検証 ✅(軽微な留保付き)

適用判定(optimizer.js:172-186):

```js
const useHoldout = testN >= 50;
const trainPhase = useHoldout ? 'train' : 'all';
...
const threshold = useHoldout ? 0 : 0.02; // 全データ学習時は2%以上の改善を要求
if (!(after < before * (1 - threshold))) { /* 適用しない */ }
```

構造は正しい: **ホールドアウトあり→未見データでの改善が判定基準(閾値0)**、**ホールドアウト不能(検証数<50)→全データ評価だが2%マージンを要求**。前者は「未見データで勝つこと自体が汎化の証拠」、後者は「訓練誤差の見かけ改善に対する保守化」で、それぞれ理にかなう。

**合成データ実験**(実コードで実行。学習者3プロファイル、各720レビュー):

| ケース | 真の記憶モデル | 結果 | 評価 |
|-------|--------------|------|------|
| A: ミスマッチ学習者(真のS=デフォルト予測×0.55) | デフォルトから乖離 | **適用** loss 0.587→0.527(holdout) | ✅ 正しく改善を検出 |
| B: 較正済み学習者(真のS=デフォルト予測×1.0) | デフォルトが最適 | 8シード中 **7回「適用しない」** | ✅ 偽陽性は低率(1/8) |
| C: コイン投げ学習者(正答率50%固定) | モデル無関係 | 適用 1.143→0.760 | ✅ 期待通り(真にデフォルトが不適合なため改善は本物) |

判定: **「改善しなければ適用しない」ガードは実験的にも機能している**。ケースBで1/8適用された点が threshold=0 の緩さを示すが、適用されたケースでも独立の新規データでの悪化は検出されなかった(harmful 0/1)。

### 4.3 留保・昇華提案 🟡

1. **threshold=0(holdout時)は無マージン**: 検証セット50件では log loss の標準誤差が ~0.05–0.1 あり、偶然の微小改善で適用され得る。**推奨: holdout時も相対1%の改善マージン**(`threshold = useHoldout ? 0.01 : 0.02`)。1行変更でB種の偽陽性をさらに抑制できる。
2. **testN≥50 は下限として小さい**: MIN_REVIEWS=300 の75/25分割なら testN≈75 が期待値であり通常は満たすが、レビューが時間的に偏ると testN<50 で全データ+2%モードに落ちる。挙動として安全側なので許容。
3. **単一分割**: ブートストラップCIやブロックドCVがあれば理想だが、端末内・数百件のデータ規模では過剰装備。現設計は**コスト対効果の均衡点として適切**。
4. **🔴 ログキャップとの相互作用**(→ §5.2): `store.js:84-85` の2万件キャップは**カード系列の先頭(初回レビュー)から削除**する。`buildSequences` は「系列の先頭=初回レビュー」を仮定してリプレイを初期化するため、キャップ発動後は**途中から始まる系列を初回として誤リプレイ**し、訓練データが系統的に歪む。ヘビーユーザー(1日200レビュー×100日で到達)ほど最適化品質が劣化する逆説的構造。

## 5. データモデル・状態遷移の整合性(E)

### 5.1 良好な点 ✅

- **カードIDのデータセット間共有**: `w-N`/`p-N` をターゲット版・全部版・Leap版で共有し、FSRS進捗が引き継がれる(app.js:66-97 `loadLeapWords`/`migrateSharedIds`)。旧 `wf-` IDのマイグレーションは `last_review` 新しい方優先(store.js `migrateCardIds`)で衝突解決も定義済み。起動時に `hasCardIdPrefix('wf-')`/`('pf-')` を検査して必要時のみ全部DBをロードする条件も正しい(app.js:175-178)。
- **状態遷移**: `new → learning/review ⇄ relearning` はFSRSの `schedule()` に一元化され、呼び出し側(session.js:352-397 `applyGrade`)は結果を透過的に保存するだけ。**遷移ロジックの二重実装がない**のは保守性上の美点。
- **ログの充実**: `s_before/d_before/s_after/d_after/format/duration_ms` まで記録(session.js:374-381)し、将来の分析・再最適化に十分な情報量。総復習回数が「解答イベント毎」にカウントされる仕様も logs.length ベース(store.js:191)で正しく実現。
- **インポートの防御**: `importData` はマージ/置換を選択させ(app.js:495-500)、不正JSONを拒否。

### 5.2 🔴 ログ2万件キャップの副作用(store.js:84-85, 265)

```js
if (logs.length > 20000) logs.splice(0, logs.length - 20000);
```

- **統計の破綻**: `stats().totalReviews = logs.length`(store.js:191)が2万で頭打ちになり、UIの「総復習回数」(views2.js:135)が静かに嘘をつく。
- **最適化データの歪み**: §4.3-4 の通り、系列先頭切断は単なるデータ減ではなく**バイアス注入**。
- **推奨**: (a) 累計カウンタを別キーで永続化し `totalReviews` に使用、(b) キャップ発動時は「カード単位で古い系列を丸ごと」落とすか、系列先頭が切れたカードをオプティマイザで除外、(c) 上限引き上げは localStorage 10MB制限(実測3.3MB/2万件)との相談。根本解はIndexedDB移行。

### 5.3 🟡 クラウド同期: READMEと実装の乖離＋ログアウト時データ破棄

- **README.md:42** は「統合(マージ)／クラウド優先／この端末優先をユーザーに確認」と記載するが、**実装は確認なしの newest-wins 自動採用**(cloud-sync.js:143-160、コメントに「確認ダイアログは出さず」と明記)。ドキュメント修正必須。挙動自体は「2端末で同日並行学習すると古い方の当日分が消える」リスクを持つ(updatedAt粒度の全置換であり、フィールド単位マージではない)。
- **ログアウト→ `Store.reset()`**(cloud-sync.js:192-196): 直前のクラウドpushが失敗していた場合(オフライン等)、ローカルの未同期分が**警告なく消える**。ログアウト時に `pushNow()` の成否を確認してから reset する1段の防御を推奨。
- 良い点: `visibilitychange`/`pagehide` でのフラッシュ、1.5秒デバウンス、`suspendDirty` による同期中の誤発火防止は堅実。

### 5.4 🟢 その他の整合性

- `stats()` の保持率は「直近200ログの grade≥3 割合」(store.js:186-188)。新規カードの初回解答や同日Again再解答も分母に含むため、**真の長期保持率より低めに出る推定量**。表示ラベルが「直近保持率」なので許容だが、`elapsed_days≥0.5` のログに限定するとFSRSの検証指標と一致し改善する。
- 成熟閾値 stability≥21日のハードコード(store.js:183 / views2.js:144 等)はAnki慣行と一致し妥当。

| `Store.getAllCards()`(604KB JSON.parse) | **7.8ms/回** | 描画・キュー生成の至る所 | 🟡 |
| `Store.addLog()`(3.3MBをparse+push+stringify) | **92.5ms/回** | **毎解答時**(session.js:374) | 🟡 |
| `wordSource()` 全deck正規化(6559件map) | 1.2ms/回 | `deckCards()` 呼び出し毎 | 🟢 |

### 6.1 🟡 解答毎のホットパスに ~100ms 超の同期I/O

`applyGrade`(session.js:352-397)は1解答で `getCard`(全parse 7.8ms)→ `setCard`(parse+stringify ~16ms)→ `addLog`(**92.5ms**)→ `incDaily` を全て同期実行する。ログ2万件到達後のモバイルでは**解答毎に200〜400msのメインスレッド停止**が見込まれ、連打時の引っかかりとして体感される。
**推奨**: (a) ログをメモリキャッシュし書き込みのみ実行(parse排除で92→~35ms)、(b) 根本的にはIndexedDBへ移行し追記型に。

### 6.2 🟡 セクション一覧描画の O(sections × N)

`renderDecks`(views.js:108-124)はセクション毎に `sectionDue()`(views.js:178-189)を呼び、その各回で `Store.getAllCards()`(7.8ms)＋ `VF.deckCards()`(**全deck正規化→filter**、app.js:153-159)を実行する。全部バージョン53セクションでは **53 × (7.8+1.2) ≈ 480ms/描画**。
**推奨**: 描画1回につき `states` と正規化済み全カードを1度だけ取得し、セクション別に集計する(O(N)化で ~10ms に短縮。変更は views.js 内で閉じる)。

### 6.3 🟢 適切な最適化がすでに施されている点

- 全部DB(5.7MB)の遅延ロード(app.js:56-65, 118-126)と設定切替時のみのフェッチ。
- ブラウズの100件ページング＋検索デバウンス200ms(views2.js:163, app.js:256-266)。
- オプティマイザの `setTimeout(0)` 逐次yield(optimizer.js:129)。
- 混同検出 `findConfusedEntry`(session.js:240-262)は線形走査だが**不正解時のみ**実行され、6559+3238件でも数ms — 許容。

## 7. UI/UX・保守性・軽微なセキュリティ(F)

### 7.1 セキュリティ 🟢(重大な問題なし)

- **XSS**: 全ユーザー由来文字列・データ由来文字列は `esc()`(views.js:5)を通過。`br()` は**エスケープ後に** `&lt;br&gt;` のみ復元する安全な設計(session.js:11, app.js:309)。入力エコー(browse-q, views2.js:205)もエスケープ済み。データJSONは静的同梱で攻撃面が小さい。
- **Supabase anonキーのハードコード**(supabase-auth.js冒頭): anonキーは設計上公開前提であり、`user_data` にRLS(own-rows policy、コメントにSQL記載)が敷かれている限り実害はない。ユーザー要望による直書きである旨のコメントも残されている。**RLSが本番で有効か定期確認すること**だけが運用上の条件。
- APIシークレットのフロント露出なし。アクセス制御をJSで模倣する構造もなし。

### 7.2 UI/UX 🟡

- **`reviewPerDay`(既定200、store.js:22)が設定UIに存在しない**(views2.js の設定画面にスライダーなし)。バックログが200件を超えた日には残余が翌日繰越になるが、ユーザーに制御手段も説明もない。
- 採点後の 1–4 キーボードショートカット(session.js:344-349)、Again強制記入、混同検出(「別の語と混同しているかも」session.js:288-298)、リーチ検出と弱点一覧(views2.js:65-101) — **学習UXは非常に丁寧**。
- グレードボタンにプレビュー間隔を表示(session.js:311-316、ファズ無し `preview()` 使用) — Anki同等の透明性。

### 7.3 保守性 🟡

- IIFE + `window.*` グローバル連結(index.tsx:69-79 の10スクリプト逐次ロード)はビルド不要で単純だが、依存が暗黙的(`views2.js` → `window.FSRSOpt` 等)。現規模(計~2900行)では許容。次の大型機能追加時にESModules化を検討。
- コメント品質が高い(設計判断の根拠・出典をコード内に明記。例: session.js:48-52 のAnkiシミュレーション引用、optimizer.js:20-25 の凍結理由)。**これは長期保守の資産**。
- キーボードリスナは `applyGrade`/`quit` で解除され(session.js:354, 439)、flashcard.js:268-270 も前ハンドラ解除を実装 — リーク対策済み。

## 9. 結論

- **アルゴリズムは妥当か** → **Yes**。FSRS-7参照実装と数式一致、キュー方針・形式ポリシーとも根拠明示付き。数値検証(境界値・単調性・状態遷移)全合格。
- **アルゴリズムは機能しているか** → **エンジンはYes。ただし入力側に穴**(#1採点欠陥、#2ログ切断)があり、放置するとモデルが静かに劣化する。
- **最適化されているか** → 設計レベルの最適化(遅延ロード・ページング・非同期yield)は良好。ホットパスI/O(#4)と一覧描画(#5)に実測裏付きの改善余地。
- **optimizer.jsの統計的健全性** → **合格**。損失関数・時系列分割・適用ガードはいずれも標準プロトコル準拠で、合成データ実験でも偽陽性1/8・真の改善検出100%。閾値マージン1行の追加でさらに堅牢化可能。
- **完成でいいか** → **#1と#2を直してから完成宣言を推奨**。両者とも半日以内の作業量で、アプリの核心価値(正確な記憶モデリング)を守るための必須投資である。
